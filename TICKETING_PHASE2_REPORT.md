## 1. Phase objective

Phase 1 defined Phase 2 as: *land the new tables without touching existing ones.*

This phase therefore implemented **only the additive ticketing database foundation**:

- the tenant chain `Organizer → OrganizerMember → Event → TicketType → EventOrder → OrderItem → Ticket`,
- the catalog prerequisites (`Sport`, `Venue`, `Event`, `EventImage`),
- ticket quota hold + order + per-attendee ticket tables,
- the payment foundation (`Payment`, `PaymentTransaction`) and the **webhook event ledger** (`WebhookEvent`),
- the PIC financial foundation (`PICProfile`, `PICEventAssignment`, `PICAttribution`, `PICFeeLedger`, `Settlement`, `SettlementItem`) and refund lines (`RefundItem`),
- notification delivery, idempotency and platform settings,
- the relation/column additions to the existing `User`, `Notification`, `Refund` and `AdminAuditLog` models.

**Not** in this phase, and not implemented: any API route, any UI, any checkout/payment/ticket workflow, any reservation or reaper service, any QR generation or scanner, any dashboard, any data backfill, and any deletion or rename of the retail domain.

Boundary, in the brief's terms: **DB = YES, API = NO, UI = NO, ticketing workflow = NO.**

## 3. Schema implemented

**27 new models / 27 new tables**, **34 new enums**. Every table is tenant-aware where the Phase 1 design requires it, every monetary column is `Decimal(14,2)`, and every new table is created with `DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci` to match the existing schema (see §13, risk BLK-2).

### How the SQL was produced

The SQL was **not** written by hand. It was generated as a diff between the committed schema and the new schema:

```
git show HEAD:prisma/schema.prisma > /tmp/schema.head.prisma
npx prisma migrate diff \
  --from-schema-datamodel /tmp/schema.head.prisma \
  --to-schema-datamodel   prisma/schema.prisma \
  --script > migration.sql
```

and then reviewed statement by statement. Exactly one edit was applied to the generated output: the `adminauditlog` collation block described in §5.3 (added with an explanatory comment in the SQL itself).

### 5.3 The one hand-written addition: collation alignment for `adminauditlog`

The generated SQL **failed** when first applied to the live database:

```
Database error code: 150
Can't create table `tinggalklik`.`adminauditlog`
(errno: 150 "Foreign key constraint is incorrectly formed")
```

Root cause (measured, not guessed): the database has **mixed collations**.

| Scope | Collation |
| --- | --- |
| 69 of 70 tables (all app tables, incl. `user`, `notification`, `refund`) | `utf8mb4_unicode_ci` |
| `adminauditlog` (the sole outlier) | `utf8mb4_0900_ai_ci` |
| Database default (`@@collation_database`) | `utf8mb4_uca1400_ai_ci` |

MySQL requires the referencing and referenced columns of a foreign key to share a character set **and** collation. `adminauditlog.actorUserId`/`organizerId`/`actorOrganizerId` therefore could not reference `user.id`/`organizer.id`. The 27 new tables were already being created as `utf8mb4_unicode_ci` (Prisma emits that explicitly), so `adminauditlog` was the only conflict.

Fix embedded in the migration (four statements, with the reasoning as a SQL comment):

```sql
ALTER TABLE `adminauditlog` DEFAULT CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
ALTER TABLE `adminauditlog`
    MODIFY COLUMN `actorOrganizerId` VARCHAR(191) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL,
    MODIFY COLUMN `actorUserId`      VARCHAR(191) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL,
    MODIFY COLUMN `organizerId`      VARCHAR(191) CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci NULL;
```

Scope of the fix: three columns that this same migration created one statement earlier (empty, nullable), plus the table's default collation. **No pre-existing column is modified, no data is rewritten, the JSON columns deliberately stay `utf8mb4_bin`, and no retail behaviour changes.** On a database with consistent collations these statements are effectively no-ops.

## 6. Indexes and constraints

### Unique constraints (the correctness guarantees)

| Constraint | Guarantee it provides |
| --- | --- |
| `WebhookEvent.providerEventId` **UNIQUE** | An exact provider redelivery cannot be processed twice (Phase 0 finding S-5). |
| `Ticket.qrTokenHash` **UNIQUE** | QR tokens are non-colliding; only the hash is stored. |
| `Ticket.ticketCode` **UNIQUE** | One printable code per admittee. |

| ID | Item |
| --- | --- |
| **V-1** | **The lesson from BLK-2:** the first scratch database was built with `prisma db push`, which produces uniform collations, so it passed a migration that the real database rejected.
