server: no SSH, no cron, no systemd unit, no PM2 process, no production environment change.

## 0. How to read this

Three kinds of statement appear here, and they are labelled:

- **CONTRACT** — how the software behaves today, verified in the tree. It is not negotiable
  by the deployment; if a step contradicts this, the step is wrong.
- **REQUIRED** — something the deployment host must provide. Omitting it breaks a documented
  behaviour.
- **OWNER ACTION** — a decision or a command that needs the repository/host owner. Phase 26
  deliberately did **not** perform these.

### 1.4 Owner actions left open by Phase 26

**OWNER ACTION — untrack two generated files.** Both are currently tracked, so the ignore

```bash

```

The files stay on disk. Next.js documents this exact action for `next-env.d.ts`
(`node_modules/next/dist/docs/01-app/03-api-reference/05-config/02-typescript.md`).

**OWNER ACTION — the stale deployment host in the origin allowlist.** `lib/app-origin.ts`
still accepts one hardcoded domain, `demosolusisejalan.my.id`, as a valid fallback origin.
Phase 26 removed the *ephemeral* tunnel hostname that sat beside it (a third party can
re-register a quick-tunnel name, which made it an open-redirect risk). This one is a real
domain: either it is this product's, in which case keep it, or it is not, in which case
delete the line. It is only ever consulted when `NEXT_PUBLIC_APP_URL` is unset.

**OWNER ACTION — unused dependencies.** `next-themes`, `@radix-ui/react-popover` and

`package-lock.json`, so it needs explicit approval and was not done here.

**OWNER ACTION — the legacy custom server.** `server.js` is dead: no script in `package.json`
references it, and it is a hand-written `http.createServer` wrapper. Do not use it as the
start command — it bypasses the supported `next start` path, and it reads `process.env.HOSTNAME`
(which on most Linux shells is already set to the machine name, so it would try to bind to the
hostname). It is either deleted or left as-is; it must not be adopted.

## 2. Node runtime contract

**CONTRACT.** Pinned in two places since Phase 26:

- `.nvmrc` → `24`
- `package.json` → `"engines": { "node": ">=20.9.0 <25" }`

The floor is not arbitrary: `next@16.3.0` declares `engines.node >= 20.9.0`. The pin records
the runtime the application is actually built and tested against (Node **24.21.0**,
npm 11.19.0 on the development machine).

**REQUIRED on the VPS**

```bash
nvm install 24          # or: nvm install    (reads .nvmrc)
nvm use                 # reads .nvmrc
node -v                 # expect v24.x
npm -v                  # expect 11.x
npx next --version      # expect 16.3.0
```

**Why a pin matters here specifically:** `package-lock.json` is `lockfileVersion: 3`, and the
Prisma client ships prebuilt engine binaries for specific platforms
(`prisma/schema.prisma` → `binaryTargets = ["native", "debian-openssl-1.0.x",
"debian-openssl-1.1.x", "debian-openssl-3.0.x"]`). A mismatched runtime is the classic source
of "works on my machine" Prisma failures.

PM2 note: PM2 must be installed and started **under the same Node** (`nvm exec` or a `pm2`
installed while `.nvmrc`'s version is active), otherwise `pm2 startup` will resurrect the app
on a different runtime after a reboot.

### 3.4 Two environment traps, both confirmed against the source

1. **`PORT` in `.env` does nothing.** `next start` resolves `-p` from `process.env.PORT`
   (`.default(3000).env('PORT')` in Next's CLI) **before** the server loads the `.env` files.
   Put the port in the process environment (`ecosystem.config.cjs` does).
2. **`HOSTNAME` is not an option — it is a CLI flag.** `next start` has no
   `.env('HOSTNAME')`; it binds `0.0.0.0` unless `-H` is passed. Meanwhile a Linux shell
   usually exports `HOSTNAME` already. The interface is therefore pinned in
   `ecosystem.config.cjs` (`-H 127.0.0.1`), not in the environment.

### 3.5 Where the environment lives

**REQUIRED:** not in the repository. Two supported shapes:

- **systemd/PM2 `env` block** (preferred), or
- a file the host loads, e.g. `/etc/tinggalklik/tinggalklik.env`, `chmod 600`,
  `chown` the PM2 user.

**Pick exactly one source of truth.** Next.js also loads `.env`, `.env.production` and
`.env.local` from the working directory at startup, so leaving a `.env` in the checkout *and*
exporting the same variables is a second source of truth that will eventually disagree.

## 4. `TRUSTED_PROXY` and the client-IP contract

This is the highest-risk item in the deployment, because getting it wrong silently disables
the login throttle.

### 4.1 What the code does

**CONTRACT** (`lib/rate-limit.ts#getClientIp`, pinned by `__tests__/security/m2-ip-spoofing.test.ts`):

- `TRUSTED_PROXY` unset → forwarding headers are ignored; **every** client is
  `"untrusted"` and shares one bucket. The login bucket is 5 attempts / 15 minutes, so this
  makes it a **platform-wide** throttle: one attacker can lock every user out.
- `TRUSTED_PROXY` set to **any non-empty value** → the **first** entry of
  `x-forwarded-for` is the client; failing that, `x-real-ip`.
- `TRUSTED_PROXY` is a **boolean switch, not an address check**. The code never compares the
  peer address to the configured value.

### 4.2 Why that is still safe — and the condition it depends on

Because the application is bound to **loopback** (`ecosystem.config.cjs` → `next start -H
127.0.0.1`), the only client that can reach it is the reverse proxy on the same host. So the
forwarding headers can only have been written by something trusted.

**REQUIRED:** set `TRUSTED_PROXY` **and** keep the loopback binding. Setting one without the
other is a regression:
- loopback + no `TRUSTED_PROXY` → everyone shares one login bucket (BLOCK-2).
- `TRUSTED_PROXY` + `0.0.0.0` → any client can forge `x-forwarded-for` and get a fresh bucket
  per request, i.e. no throttle at all.

### 4.3 The reverse proxy must OVERWRITE `x-forwarded-for`, not append

`getClientIp` reads the **first** comma-separated entry. nginx's common idiom,

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # APPENDS
```

*appends* the real peer to whatever the client sent, so the header becomes
`<attacker-supplied>, <real client ip>` and the application reads the **attacker's** value.
That restores the per-request bucket and defeats the limiter — through a header, without
touching the application.

**REQUIRED nginx configuration:**

```nginx
server {
    listen 443 ssl http2;
    server_name YOUR_HOST;

    # Uploaded event images are capped at 5 MB by the application
    # (lib/images/process.ts → MAX_EVENT_IMAGE_BYTES). nginx's default is 1m,
    # which would reject a legal upload with 413 before it ever reaches the app.
    client_max_body_size 8m;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Forwarded-Proto $scheme;

        # OVERWRITE (not $proxy_add_x_forwarded_for). See §4.3.
        proxy_set_header X-Forwarded-For   $remote_addr;
        proxy_set_header X-Real-IP         $remote_addr;
    }
}
```

With a second proxy in front of nginx (Cloudflare, a load balancer), `$remote_addr` is that
proxy, not the visitor. In that case use nginx's `real_ip` module to rewrite the client
address first, and keep the `proxy_set_header` lines above unchanged:

```nginx
set_real_ip_from  <cloudflare-or-lb-cidr>;
real_ip_header    CF-Connecting-IP;   # or X-Forwarded-For, per provider
real_ip_recursive on;
```

### 4.4 Verification

From the host (replace `HOST`):

```bash
# 1. TRUSTED_PROXY is set in the running process' environment (name only, never the value):
sudo tr '\0' '\n' < /proc/$(pgrep -f 'next start' | head -1)/environ | grep -c '^TRUSTED_PROXY='

# 2. A forged header must NOT create a distinct bucket. These are all the SAME client:
for i in 1 2 3 4 5 6; do
  curl -s -o /dev/null -w '%{http_code} ' \
    -X POST https://HOST/api/auth/callback/credentials \
    -H 'x-forwarded-for: 203.0.113.250'
done; echo
```

If the sixth attempt is still being processed rather than throttled, the bucket is not being
keyed by client and §4.3 is wrong.

**Symptom of a misconfigured deployment:** the first five failed sign-ins *from anywhere in
the world* block sign-in for everyone for 15 minutes.

## 5. Health and readiness

Added in Phase 26 (Phase 25 BLOCK-5 found no health endpoint at all).

| Endpoint | Meaning | Status | Calls |
|---|---|---|---|
| `GET /api/health` | **liveness** — the process answers HTTP | always `200` | nothing |
| `GET /api/health/ready` | **readiness** — the process can serve | `200` or `503` | one `SELECT 1` |

**CONTRACT.** Both are public by design: a probe holds no session. Neither returns a version,
a hostname, an environment name, uptime, dependency detail or any business data; readiness
logs its sanitised diagnosis **server-side only** (`lib/errors/infrastructure.ts`
`classifyInfrastructureFault`, whose `detail` never contains the driver message). Neither
mutates anything and neither calls iPaymu.

**Why two endpoints.** A liveness probe answers "should this process be restarted?". A
database outage cannot be fixed by restarting Node, so `GET /api/health` deliberately touches
nothing — otherwise a process manager would restart-loop a healthy server and turn one fault
into two. Use `/api/health/ready` where "can I send traffic?" is the question.

**Usage**

```bash
curl -fsS https://HOST/api/health          # deployment smoke test: process is up
curl -fsS https://HOST/api/health/ready    # deployment gate: database reachable
```

- Uptime monitor / PM2 liveness → `/api/health`
- Deployment gate and load balancer → `/api/health/ready`
- A `503` from readiness means *do not roll traffic to this instance*, and the log line says
  which fault class it was.

## 6. Upload persistence and backup

### 6.1 How storage actually works

**CONTRACT**

- Writers: **only** `lib/images/process.ts` (`processAndStoreEventImage`), called by the
  organizer image routes. It writes to `<UPLOAD_DIR>/events`, defaulting to
  `./storage/uploads/events` **relative to the process working directory**.
- Names are generated server-side (`Date.now()` + 16 random bytes + a format-derived
  extension); the client's filename never reaches the filesystem.
- The **original upload is never written to disk** — validation, EXIF/metadata stripping and
  storage all happen in memory (decision D-55), so only the processed bytes exist.
- Serving is by the application, not by nginx: `GET /api/uploads/events/<name>`, public by
  contract (catalog banners and Open Graph cards need it without a session), `immutable`
  cache headers, `X-Content-Type-Options: nosniff`, basename-only path resolution.
- The database references each file by URL in the image row. **The file exists only on disk.**

### 6.2 REQUIRED: a persistent path outside the checkout

The default `./storage/uploads` resolves inside the repository directory. That is a problem
precisely because deploys replace the checkout:

- a `git clean`/fresh clone/`rsync --delete` deploy would **delete every uploaded image**
  while the database rows still point at them → broken banners across the whole catalog;
- PM2 restart/reload does **not** touch it, so restarts are safe either way.

**REQUIRED:** set `UPLOAD_DIR` to an absolute path outside the checkout:

```
UPLOAD_DIR="/var/lib/tinggalklik/uploads"
```

```bash
sudo mkdir -p /var/lib/tinggalklik/uploads
sudo chown -R <pm2-user>:<pm2-user> /var/lib/tinggalklik/uploads
sudo chmod 755 /var/lib/tinggalklik/uploads
```

Ownership must be the PM2 user (the process must be able to create `<UPLOAD_DIR>/events`).

### 6.3 Backup contract

**REQUIRED.** Uploads and the database are one asset in two places: a row without its file is
a broken banner, a file without its row is an orphan. **Back them up in the same window.**

```bash
# Both, in one window, with a matching timestamp.
STAMP=$(date -u +%Y%m%dT%H%M%SZ)

# 1. Uploads
tar -czf /var/backups/tinggalklik/uploads-$STAMP.tar.gz \
    -C "$(dirname "$UPLOAD_DIR")" "$(basename "$UPLOAD_DIR")"

# 2. Database — same window
mysqldump --single-transaction --routines --triggers \
    "$DB_NAME" | gzip > /var/backups/tinggalklik/db-$STAMP.sql.gz
```

- `--single-transaction` keeps the dump consistent without locking writes (InnoDB).
- The `uploads-*.tar.gz` and `db-*.sql.gz` with the **same `$STAMP`** are the restore unit.
- Copy both off the host. A backup on the same disk is not a backup.
- **No cloud storage provider is introduced**: this is `tar` + `mysqldump` to a path the
  operator chooses.

**Restore expectation**

```bash
systemctl stop tinggalklik    # or: pm2 stop tinggalklik
tar -xzf /var/backups/tinggalklik/uploads-$STAMP.tar.gz -C /
gunzip -c /var/backups/tinggalklik/db-$STAMP.sql.gz | mysql "$DB_NAME"
systemctl start tinggalklik   # or: pm2 start tinggalklik
curl -fsS https://HOST/api/health/ready
```

Restoring only the database leaves image rows pointing at files that may not exist; restoring
only the uploads leaves orphans. Restore the pair.

**A restore drill is an owner action** — it has not been performed, because it would require
a server. Perform it once before going live: an untested backup is a hypothesis.

## 7. PM2 / startup contract

**REQUIRED:** `ecosystem.config.cjs` is the process definition (see that file for why it is
`node_modules/next/dist/bin/next` rather than `npm start`, and why it is **one forked
instance** — `lib/rate-limit.ts` is an in-memory limiter, so a second instance would silently
double every rate limit).

```bash
cd /srv/tinggalklik                 # the checkout
pm2 start ecosystem.config.cjs
pm2 reload tinggalklik              # after a new build
pm2 save                            # persist the process list
pm2 startup                         # print + install the boot hook (run as root)
pm2 logs tinggalklik                # timestamps are enabled
pm2 status
```

| Concern | Where |
|---|---|
| Listens on | `127.0.0.1:${PORT}` (default 3000) |
| Logs | `~/.pm2/logs/tinggalklik-{out,error}.log` |
| Log rotation | not included: `pm2 install pm2-logrotate`, then set `max_size` / `retain` |
| Restart after reboot | `pm2 startup` once, then `pm2 save` after every process change |
| Crash behaviour | `autorestart: true`; a crash-loop is visible in `pm2 status` as a rising restart count |

**Note:** `pm2 reload` on a single fork-mode instance is effectively a restart. That is
acceptable (a few hundred milliseconds) but it is not zero-downtime; do not describe it as
such to users. Zero-downtime would require clustering, which the in-memory limiter forbids.

## 8. Prisma migration deployment contract

**CONTRACT.** 23 migrations, all committed, local database up to date. Prisma resolves
`DATABASE_URL` from the schema at connect time.

**REQUIRED — the only supported command on a server:**

```bash
npx prisma migrate deploy
```

**Never** on a deployment host: `prisma migrate dev` (can prompt and can reset),
`prisma migrate reset`, `prisma db push` (bypasses history and causes drift).

**Generated client.** `@prisma/client` has a `postinstall` hook that generates the client, so
`npm ci` generates it. Run it explicitly anyway if `node_modules` was restored rather than
installed:

```bash
npx prisma generate
```

### 8.1 The first deploy runs a DESTRUCTIVE migration

**REQUIRED ATTENTION.** `20260920000000_drop_unused_legacy_retail_tables` **drops tables**. It
is already applied to the local development database, so on a **fresh** production database
the migration history would replay from the baseline; on a database that already carries the
legacy retail tables, this migration is the one that removes them.

**Take the §6.3 backup immediately before `migrate deploy`, every time.** On the first deploy
that is not a formality — it is the difference between a recoverable and an unrecoverable
outcome.

### 8.2 Rollback reality — state it plainly

**Prisma has no down-migrations.** `migrate deploy` applies forward only. There is no
`prisma migrate rollback`. A migration that has run is, from Prisma's point of view,
permanent.

Consequences:

- Rolling back the **application** is `git` + `npm ci` + `npm run build` (§9.4). It does not
  undo a migration.
- Rolling back the **schema** means **restoring the pre-deploy database dump**. That discards
  every write since the dump — orders, payments, tickets, refunds — so it is a business
  decision, not a deployment step.
- Do **not** hand-write "reverse SQL" as a rollback plan. A hand-written inverse is untested,
  may not preserve data, and will not update Prisma's `_prisma_migrations` table unless it is
  written as a real migration — which makes the history disagree with the schema.

## 9. Deployment runbook

Replace `HOST`, `/srv/tinggalklik`, `<pm2-user>`, `$DB_NAME` and `$UPLOAD_DIR`.

### 9.1 PRE-DEPLOY

```bash
# 0. Decide the release and record it (this is what rollback returns to).
ssh deploy@HOST 'cd /srv/tinggalklik && git log --oneline -1 && git status --porcelain'
#   ↑ working tree must be CLEAN. A deploy from a dirty tree is unreproducible.

# 1. Node
nvm use    # .nvmrc → 24;  node -v must be v24.x

# 2. Disk space — a build plus a migration plus a dump needs headroom
df -h /

# 3. Environment presence (names only; never print values)
sudo tr '\0' '\n' < /proc/$(pgrep -f 'next start' | head -1)/environ \
  | grep -oE '^(DATABASE_URL|AUTH_SECRET|AUTH_URL|NEXT_PUBLIC_APP_URL|PAYMENT_ENVIRONMENT|IPAYMU_PRODUCTION_VA|IPAYMU_PRODUCTION_API_KEY|JOBS_TICK_SECRET|TRUSTED_PROXY|UPLOAD_DIR)=' | sort

# 4. Backups — BOTH, same window (§6.3). Do not skip.
STAMP=$(date -u +%Y%m%dT%H%M%SZ)
tar -czf /var/backups/tinggalklik/uploads-$STAMP.tar.gz -C "$(dirname "$UPLOAD_DIR")" "$(basename "$UPLOAD_DIR")"
mysqldump --single-transaction --routines --triggers "$DB_NAME" | gzip > /var/backups/tinggalklik/db-$STAMP.sql.gz
echo "$STAMP" > /var/backups/tinggalklik/LAST_PRESTAGE_DEPLOY_STAMP

# 5. Migration state BEFORE touching anything
cd /srv/tinggalklik && npx prisma migrate status

# 6. TLS and DNS
curl -fsSI https://HOST/ | head -1        # expect 200/301, not a cert error
```

### 9.2 DEPLOY

```bash
cd /srv/tinggalklik

git fetch --all --tags
git checkout <release-sha-or-tag>          # not "git pull" — check out a known commit
git log --oneline -1                       # confirm what is about to run

npm ci                                     # exact install from package-lock.json
npx prisma migrate deploy                  # FORWARD ONLY — see §8.2
npx prisma migrate status                  # must report "up to date"
npx prisma generate                        # idempotent; belt and braces
npm run build                              # needs the DB reachable
pm2 reload tinggalklik
```

### 9.3 VERIFY

```bash
curl -fsS https://HOST/api/health          # process up
curl -fsS https://HOST/api/health/ready    # database reachable  ← the deployment gate
curl -fsSI https://HOST/ | grep -iE 'strict-transport-security|content-security-policy'
curl -fsS https://HOST/api/events | head -c 200   # public catalog answers
```

Then, by hand (they need a session):

1. **Sign in** as a known account of each role that exists on the server.
2. **Dashboard loads** for an ADMIN/MANAGER; a CUSTOMER sees the access-denied surface, not a
   crash.
3. **Own order page** renders for its buyer; a different account gets 404 (the Phase 23A
   contract).
4. **Upload serving** — request an existing banner URL and confirm a 200 with an image
   content type.
5. **Rate limiting** — §4.4.

### 9.4 ROLLBACK

**Application rollback** (correct and cheap):

```bash
cd /srv/tinggalklik
git checkout <previous-release-sha>
npm ci
npm run build
pm2 reload tinggalklik
curl -fsS https://HOST/api/health/ready
```

**Database:** there is no rollback. Either accept the migration (the usual answer — Prisma
migrations in this repository are additive except the one drop in §8.1) or restore the
pre-deploy dump, accepting the loss of every write since:

```bash
gunzip -c /var/backups/tinggalklik/db-<STAMP>.sql.gz | mysql "$DB_NAME"
```

**Uploads:** code rollback does not touch them. If a rollback also restored the database, the
images written since the dump become orphans — harmless, and reclaimable later by comparing
the directory against the image rows. Only restore `uploads-<STAMP>.tar.gz` if files were lost.

**When a full restore is required:** schema restored from a dump *without* the corresponding
uploads tarball — that is the only case where the two halves must be restored together.

## 10. Scheduler gate

**The scheduler is NOT installed, and a later phase installs it — not this one.**

`POST /api/internal/jobs/tick` is the only driver of two behaviours that are otherwise
silently inert:

- event lifecycle transitions (`PUBLISHED → ONGOING → COMPLETED`) — without them an event
  never completes;
- reservation expiry (releasing held seats from abandoned checkouts) — without it events
  appear sold out.

The contract is fixed and must not be re-designed: `POST /api/internal/jobs/tick` with
`Authorization: Bearer $JOBS_TICK_SECRET`, one request per minute, constant-time comparison,
fails closed (`401`) when the secret is unset, one-row-per-job lease in the `joblock` table.
The full procedure is in `README.md` §1.

**Install the schedule only when ALL TEN conditions hold:**

1. The application is deployed to the VPS and reachable over HTTPS.
2. Production HTTPS works with a valid certificate (not a bypassed warning).
3. The production environment is verified — §3.1 present, `PAYMENT_ENVIRONMENT=production`.
4. `JOBS_TICK_SECRET` is configured (32 random bytes) and present in the *running* process.
5. `POST /api/internal/jobs/tick` returns `401` **without** the header and `200` **with** it.
6. `/api/health` and `/api/health/ready` both answer correctly.
7. `npx prisma migrate status` reports the schema up to date.
8. PM2 persistence/startup is verified — a reboot brings the app back (`pm2 save` + `pm2 startup`).
9. Upload persistence is verified — `UPLOAD_DIR` is outside the checkout and survives a deploy.
10. The release is accepted as production-ready.

**Then verify the jobs actually ran** (there is no UI):

```sql
SELECT name, lastRunAt, lastStatus, lockedUntil FROM joblock;
```

`lastRunAt` is `NULL` on a live deployment only when the schedule is missing or failing.
